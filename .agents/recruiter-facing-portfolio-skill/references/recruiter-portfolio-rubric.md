# Recruiter Portfolio Review Rubric

Use this reference when a task needs a full recruiter-facing audit or when deciding between competing portfolio changes.

## 1. Positioning

A hiring manager should understand the intended role in seconds.

Check:
- page title
- hero title
- supporting headline
- opening paragraph
- navigation labels
- selected project mix
- About opening
- contact examples
- SEO description

Penalty:
- mixed target roles without a coherent umbrella
- generic "software engineer" copy that conflicts with a more specific target
- "aspiring", "learning", or course-heavy language dominating experienced positioning

## 2. Evidence hierarchy

Rank evidence roughly as:
1. completed/deployed work the candidate can defend
2. real production or customer-facing experience
3. technically substantial completed personal work
4. work in progress with concrete architecture and current status
5. planned work
6. course progress

Course completion is not a substitute for implementation proof.

## 3. Project selection

Prefer projects demonstrating several of:
- API/integration work
- authentication
- databases
- AI/LLM integration
- customer/business workflow
- deployment
- payments
- serverless architecture
- mobile/full-stack implementation
- reliability/observability decisions
- human review or operational safety

Do not invent a "better" project to satisfy a portfolio pattern.

## 4. Status integrity

Possible labels include:
- Deployed
- Completed
- Currently building
- Build brief
- Planned

Only choose labels supported by evidence.

For unfinished work, favor:
- Problem
- Proposed solution
- Planned architecture
- Current status
- Next milestone

Avoid empty:
- Architecture
- Decisions
- Results

tabs when they only contain "coming soon" copy.

## 5. Metrics

For each number, ask:
- Where did this number come from?
- Can the candidate defend it under interview questioning?
- Is it documented, strongly remembered, estimated, or invented?
- Does the current public wording imply more certainty than the evidence?

If uncertain, use accurate non-numeric language rather than a fake precision upgrade.

## 6. Homepage signal

Strong homepage:
- specific target identity
- short value proposition
- proof-oriented CTA
- completed evidence appears early
- relevant prior experience supports the new target
- unfinished work is secondary and explicit

Weak homepage:
- public accountability dashboard
- multiple 0% indicators
- unfinished project featured first
- empty case-study tabs
- biographies before relevance
- generic contact copy that contradicts target role

## 7. About / career narrative

Recommended order:
1. current implementation value
2. why support / enterprise / SRE / product background helps
3. career development
4. personal story

The goal is coherence, not erasing earlier experience.

## 8. Design restraint

A visually strong portfolio usually does not need another redesign.

Only change visual structure when it improves:
- scanability
- information hierarchy
- accessibility
- proof visibility
- responsiveness

Do not confuse novelty with hiring value.

## 9. Final test

Ask:

"After 30–60 seconds, what would a skeptical hiring manager believe this person can do today?"

If the strongest answer is "take courses" or "plans to build", the portfolio still has an evidence problem.
